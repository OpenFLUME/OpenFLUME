# Why a thermo-fluid solver should run in the browser

_John Rising · 2026-12-01_

Engineering solvers have traditionally been desktop programs: licensed per seat, installed by an administrator, sometimes tied to one operating system. Newer ones run in the cloud, where your model goes up and results come back. OpenFLUME runs the whole solver in a browser tab, on your machine, from static files.

Architecture details come from [docs/architecture.md](../architecture.md); performance numbers come from [docs/real-fluid-performance.md](../real-fluid-performance.md), regenerated by `npx tsx scripts/real-fluid-performance.ts`.

## Design goals

I wanted three properties, and the browser is the only platform I know of that provides all of them.

**Zero install.** Anyone, including an engineer on a locked-down laptop, can follow a link and be solving a network seconds later, with no license server, administrator rights, or account. If I send someone a model, they can run it.

**Local-first.** The app is static files on GitHub Pages, the solver runs in your browser, and models are saved to local files and browser storage, so nothing is uploaded and you can verify that yourself. Running locally keeps model data on your machine; it doesn't by itself settle export-control questions, which remain yours to judge.

**One core, many hosts.** The same TypeScript solver runs in the browser worker, in Node for the test suites, and in Python through a bundled Node runtime, so there is one implementation and one verification record.

## Architecture

### The solver runs in a Web Worker

Each browser solve runs in its own module worker. The UI sends a structured clone of the model and mode; the worker validates the model, initializes CoolProp only if the network needs it, posts throttled progress messages, and returns the result. The worker is terminated when the solve settles (done, error, or crash) or is cancelled, so idle workers never pile up.

Because the solve loop is synchronous, **Cancel terminates the worker and spawns a fresh one.** Cooperative cancel would need `SharedArrayBuffer`, which requires cross-origin isolation headers a static host doesn't send by default. Terminate-and-respawn is blunt but always works, and a cancelled transient keeps its partial trajectory, labeled as partial.

The worker keeps the UI responsive but does not sandbox code. User-authored components run as trusted JavaScript through `new Function`. As defense in depth, the worker strips network-capable globals (`fetch`, `XMLHttpRequest`, `WebSocket`, `indexedDB`, `caches`, and others) before any solve. That reduces accidental risk but does not make hostile code safe, so treat a model file that contains code like source code.

### CoolProp, compiled to WebAssembly

Real-fluid properties come from `coolprop-wasm`: MIT-licensed, covering the cryogenic and propulsion fluids I needed, with saturation and analytic-derivative APIs, and running in both Node tests and browser workers. The worker lazy-loads it only for models that use a real fluid, so a water-distribution model never downloads it.

### Local-first persistence

Models save as `.fn` files, a line-oriented, lossless text format that diffs cleanly in version control. The browser autosaves your current model and mirrors run results so a reload resumes the session. **Save** also writes a portable `<model>.runs.json` sidecar with each run's config snapshot, result, and solver diary. Browser storage is not a backup; save the `.fn` file and sidecar if the work matters.

### The Python package bundles the same core

`pip install openflume` does not reimplement the solver ([docs/python.md](../python.md)). It bundles the core, the `.fn` parser, and the examples into one JavaScript file alongside `coolprop.wasm`, run by a Node.js runtime delivered as a pip dependency, and talks to it over newline-delimited JSON on stdin and stdout. Results match the TypeScript library exactly and the browser to floating-point rounding (JavaScript engines may differ in the last bit of `Math.*` functions), so every verification result applies unchanged.

## Performance

A JavaScript solver calling a WebAssembly property library sounds slow. `real-fluid-performance.md` profiles four real-fluid solves on one machine:

| Case                                 | Hybrid wall time | Share in property evaluation |
| ------------------------------------ | ---------------- | ---------------------------- |
| LN₂ two-phase chilldown (first 75 s) | 167 ms           | 18.3 %                       |
| LN₂ chilldown, full 300 s horizon    | 1.34 s           | 74.9 %                       |
| N₂O cavitating venturi               | 30 ms            | 12.2 %                       |
| N₂ transonic C-D nozzle              | 40 ms            | 7.0 %                        |

Identical solves have differed by up to about 1.7× across machines and loads, so treat absolute wall times as indicative. Property-call counts repeat exactly.

**The analytic Jacobian cuts property calls.** The default `hybrid` Jacobian builds real-fluid derivatives analytically, with one state and one derivative evaluation per node per build instead of a residual sweep per column. Against finite differences it makes **2.75×–70.63× fewer property calls** on these cases and converges to the same trajectories. The wall-clock speedup was 1.53×–6.78× on that machine, depending on load.

**Hot paths use CoolProp's cached-state interface.** A full `PropsSI` round trip costs 9.29× more than a flash on a cached `AbstractState`, so the solver uses the cached interface behind a bounded 8,192-entry cache keyed on `(fluid, P, h)`.

**Porting the solver would not make it fast.** I find this the most interesting result. Wall times are 30 ms–1.34 s, and on long horizons the dominant cost is first-visit CoolProp flashes, which a compiled-language port would not touch. The remaining solver time is spread across residual assembly, state cloning, and bookkeeping with no single hotspot; dense Gaussian elimination takes 0.4 %–4.3 % of wall time. Even a faster property backend has a hybrid-path ceiling of 1.08×–3.98× on these cases, and a port "would forfeit the browser-worker deployment." The report recommends revisiting only with a profile of a real workload that is still too slow.

The cost you will notice is the WebAssembly compile on the first CoolProp call in a fresh process, 1.67 s in that report, which short transients feel as a fixed per-solve overhead.

## Trade-offs

- **No cooperative cancellation.** Killing the worker is fine for a UI and awkward for some embedding hosts. The Python package behaves the same way: Ctrl-C kills the Node process, and the session restarts on its next call.
- **Single-threaded solves.** Parameter sweeps run their variants sequentially, one worker each, so a real-fluid sweep reloads CoolProp per variant; a warm-worker pool is a possible future optimization. In Python, parallelism means one session per process.
- **Session-scoped exploration.** Sweeps are session-only by design; promote a sweep point to a saved variant to keep it.

The physics scope has its own, more important limits ([§1.7 Scope Boundaries](../user-manual.md#_1-7-scope-boundaries)): no shock capture, no acoustic wave propagation, HEM-only two-phase flow, cavitation only at the venturi closure, a pump curve for turbomachinery, and no general junction mixing.
