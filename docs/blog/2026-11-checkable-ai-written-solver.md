# Building a thermo-fluid solver with AI assistance, and how it is verified

_John Rising · 2026-11-24_

I wrote OpenFLUME alone with heavy AI assistance over a short calendar period, as the README states. Network codes fail quietly: a wrong sign in an energy balance, a badly scaled residual, or a convergence test that passes for the wrong reason still produces a reasonable-looking plot. Because plausible code was cheap to generate, the design problem became what has to exist for someone else to tell whether it is correct.

## Three classes of evidence

Each verification case belongs to one of three classes and is labeled accordingly ([user manual §8.1](../user-manual.md#_8-1-approach)):

1. **Analytic verification** compares against a closed-form or independently integrated solution, such as Hagen–Poiseuille, the Fanno relations, an exponential lumped cooldown, or a Runge–Kutta reference for a tank blowdown. A disagreement means OpenFLUME is wrong.
2. **Code-to-code benchmarking** compares against published GFSSP or SINDA/FLUINT results. Agreement supports the implementation but inherits the other code's assumptions, and two codes can share an error.
3. **Validation against experiment** compares against digitized test data. A disagreement could come from the model, the closure correlation, the discretization, or the experiment.

"Agrees with GFSSP within 5 %" and "agrees with experiment within 5 %" are different claims, and an analytic match to machine precision is a third kind. Mixing them overstates a verification record. Where a case doesn't fit cleanly, the documentation says which class it is in and why: the GFSSP compressible-flow recreation is filed under analytic verification, because every number in it is graded against an RK4 reference instead of GFSSP output.

## Reports generated from live solves

The seven validation reports in `docs/validation/` are generated, not written. A script in `scripts/` builds each report's cases, solves them with the current solver, and writes the tables and SVG figures. The compressible report opens with "Generated by `scripts/compressible-validation-report.ts` — all numbers and figures come from live solves of the current solver," and names its CI gate.

A language model will readily write "agrees within 1 %"; a script that solves the case can only print what the solver returns. When the solver changes, the report changes, and a regression shows up in the diff.

## One-click analytic examples

Some checks live in the app. The first menu example, [Sanity: orifice hand-calc](https://openflume.github.io/OpenFLUME/#example=sanity-orifice-hand-calc), is two boundaries and one orifice, with the expected answer, `C_d·A·√(2ρΔP) ≈ 0.8485 kg/s`, written on the canvas. Click **Run**, select the branch, and compare. The manual calls it "the smallest case that exercises the whole chain — decode, validate, assemble, Newton solve, report" ([§7.1](../user-manual.md#_7-1-sanity-orifice-hand-calc)).

The source tree exports more hand-checkable cases that stay out of the menu: a hydrostatic column, a 50/50 split, equal-temperature mixing, tank equalization, and a conduction ladder with lumped cooldown. The test suites assert on them with published tolerances of 10 Pa on the hydrostatic column, 0.001 kg/s on the split, and 0.05 K on mixing ([§8.2](../user-manual.md#_8-2-analytic-verification)).

## CI tiers

The tiers are defined in [CONTRIBUTING.md](../../CONTRIBUTING.md), [docs/testing-slow.md](../testing-slow.md), and the CI workflow:

| Tier               | What it runs                                                                                             | When CI runs it                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `npm test`         | Fast tier: component, solver, configuration, UI, server, workflow tests; excludes whole scientific files | Every pull request (`check` job, with lint, format, typecheck, production build) |
| `npm run test:all` | Every Vitest file, including real-fluid, two-phase, chilldown, venturi, and benchmark suites             | Every pull request (`scientific-validation` job)                                 |
| `RUN_SLOW=1`       | Adds opt-in blocks: full NBS chilldown baselines, cavitating-venturi sweeps, two-phase staircases        | Pushes to `main`, weekly schedule (Mondays), manual dispatch                     |
| Playwright e2e     | Full browser suite against the production build                                                          | Every pull request, four shards                                                  |
| Python wheel       | Installed-wheel tests on Linux, macOS, Windows                                                           | Every pull request                                                               |

The fast tier excludes expensive scientific suites by whole file instead of by test-name filter, so that "suite membership is reviewable and stable" ([architecture](../architecture.md)). The demo site deploys only after a green CI run on `main`, so a failing build can't reach the published app.

This setup is recent. According to the 0.2.0 changelog entry, the scheduled job "now runs the slow scientific suite (`RUN_SLOW=1`) and the full Playwright e2e suite (previously never run anywhere)."

## Defects verification caught

Most of the serious defects in the [CHANGELOG](../../CHANGELOG.md) are false successes: something reported as converged, valid, or computed when it wasn't.

- **Microfluidic transients froze while reporting convergence** (0.3.0). The Newton stopping test compared an absolute tolerance against residual rows in kg/s. At microfluidic flows (~1e-8 kg/s) every mass imbalance already passed, so steps were accepted at their warm start. A validation case caught it: a bubble-damped syringe network from Lee et al. (2012), checked against its exact ODE. Before the fix the error was 1.2 % at tol 1e-9 and 37 % at the UI default of 1e-6; afterwards it was under 1e-3 at both ([microfluidics report](../validation/microfluidics-report.md), case B6).
- **Transient steps were certified as converged unconditionally** (0.2.2). For incompressible, ideal-gas, and compressible-liquid networks, a step was labeled `converged` without checking that the inner Newton had met its residual bar. This hid a real failure in the **Entrapped-air line** example: its first step couldn't balance the momentum rows, because a warm-start guess was being used as an initial condition behind a closed valve.
- **A failed chemistry sub-step was silently swallowed** (0.2.2). The node stayed at its pre-reaction state inside a step certified as converged.
- **A fabricated property state could reach an accepted result** (0.2.2). A last-resort fallback (`T = 300 K, ρ = 100 kg/m³`), there only to avoid a WebAssembly crash, could pass through unnoticed. Steady solves now report `converged: false` with a fallback count.
- **A fabricated critical point was cached for the life of the process** (0.2.0). A failed CoolProp critical-point read cached `Pc = 1e7 Pa, Tc = 300 K`, misrouting every later phase-region decision. It now throws.
- **An unknown convection model was evaluated as Darr–Hartwig** (0.2.0) instead of raising an error.
- **The reported ΔP under `momentumFlux` was not the solved ΔP** (0.2.0). It was re-derived from a legacy formula that disagreed with the default scheme.
- **A sweep could run embedded code that the Run button would have blocked** (0.2.2, security). Sweeps now go through the same trust preflight.

The validation data had errors too. The header of the NBS chilldown dataset module (`src/validation/nbsChilldown.ts`) records that an early comparison used a model node about 40.6 m down the line against Table 6, which is defined at station 4, 60.35 m from the inlet; the mismatch produced a confounded "−27 %…−32 %" error. The same header notes that a raw-data catalogue listed the thermocouple stations wrongly. Both primary sources agree on 20/80/141/198 ft.

The repository doesn't record which lines a model drafted and which I typed. What the list does show is a consistent failure shape: code that looks complete, returns a number, and reports success. Each defect is pinned by a regression test, and several fixes took the same form, replacing a silent fallback with a loud failure.

## Trust levels on experimental data

The NBS Report 9264 chilldown corpus has 18 Table-6 chilldown-time points and 44 digitized station traces from eleven oscillograph figures. They are not pooled ([§8.4](../user-manual.md#_8-4-validation-against-experiment)):

- **Four saturated runs (sixteen traces) are trusted**, meaning calibration-grade.
- **Seven subcooled runs are diagnostic only.** At coarse axial discretization their errors reach +80 %. They can inform a diagnosis but are not quoted as agreement.

The code enforces this: the corpus validator throws if a subcooled run isn't marked `diagnosticOnly`. Per-trace QC flags further restrict which features of a trusted trace can be used, because the NBS report warns that some low-temperature curve crossings are measurement inaccuracies.

## Labeling what is not validated

Every convection correlation has a status in [§8.5](../user-manual.md#_8-5-correlation-status). Dittus–Boelter is standard. Darr–Hartwig is verified structurally against the published equations, with its fitted envelope (LH₂, vertical upflow, 1 g) stated. TT-WF, my own design, is labeled **"Research status, not validated."** A custom expression has "no published range; the user owns its validity."

Production solver code may not import from `src/validation`, and lint rules check this. Validation corpora "must not silently tune runtime defaults to a single experiment" ([architecture](../architecture.md)), since a solver tuned to the data it is validated against hasn't been validated by that data.

## What AI assistance did and didn't do

AI assistance made a large surface area cheap to produce: 19 component types, seven report generators, and the test scaffolding around them. It didn't make that code correct; the verification suite found the defects above, most of which produced plausible-looking results.
