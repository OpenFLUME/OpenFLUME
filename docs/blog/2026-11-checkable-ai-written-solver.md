# I built a thermo-fluid solver with AI. Here's how I made it checkable.

_John Rising · 2026-11-24_

OpenFLUME was written by one engineer with heavy AI assistance, over a short calendar period. That is in the README, and I'm not going to soften it here. A thermo-fluid solver is exactly the kind of code where that should make you suspicious. Network codes fail quietly. A wrong sign in an energy balance, a residual that is scaled badly, or a convergence test that passes for the wrong reason will still produce a plot that looks reasonable.

So the design question was never "how do I get AI to write a solver?" It was this: when producing plausible-looking code is cheap, what has to exist so that somebody else can tell whether the code is _correct_? This post describes the answer as it exists in the repository, and the defects it has caught.

## Three kinds of evidence, never mixed

Each verification case in OpenFLUME belongs to exactly one of three classes, and it is labeled that way ([user manual §8.1](../user-manual.md#_8-1-approach)):

1. **Analytic verification.** The comparison is against a closed-form or independently integrated solution, such as Hagen–Poiseuille, the Fanno relations, an exponential lumped cooldown, or a Runge–Kutta reference for a tank blowdown. If OpenFLUME disagrees, OpenFLUME is wrong.
2. **Code-to-code benchmarking.** The comparison is against published GFSSP or SINDA/FLUINT results. Agreement supports the implementation, but it inherits the other code's assumptions. Two codes can share an error.
3. **Validation against experiment.** The comparison is against digitized test data. A disagreement could come from the model, the closure correlation, the discretization, or the experiment.

Keeping these apart is the core of the whole design. Mixing them is how a verification record ends up overstating itself. "Agrees with GFSSP within 5 %" and "agrees with experiment within 5 %" are very different claims, and an analytic match to machine precision is a different kind of statement again. When a case does not fit cleanly, the documentation says so. The GFSSP compressible-flow recreation, for example, is filed under _analytic_ verification, because every number in it is graded against an RK4 reference rather than GFSSP output.

## Reports generated from live solves

Seven validation reports live in `docs/validation/`. None of them is written by hand. Each is generated by a script in `scripts/`, which builds the cases, solves them with the current solver, and writes the tables and SVG figures. The compressible report, for instance, opens by saying it was "Generated by `scripts/compressible-validation-report.ts` — all numbers and figures come from live solves of the current solver," and it names its CI gate.

This matters more for an AI-assisted codebase than for most. A model is good at producing a confident paragraph that says "agrees within 1 %." A script that solves the case and prints the number cannot do that. If the solver changes, the report changes. If the numbers get worse, the diff shows it.

## Analytic sanity examples you can run in one click

Some of the evidence lives in the app itself, not in documents. The first example in the menu is [Sanity: orifice hand-calc](https://openflume.github.io/OpenFLUME/#example=sanity-orifice-hand-calc). It is two boundaries and one orifice, with the expected answer, `C_d·A·√(2ρΔP) ≈ 0.8485 kg/s`, written on the canvas. Click **Run**, select the branch, and compare. The manual describes it as "the smallest case that exercises the whole chain — decode, validate, assemble, Newton solve, report" ([§7.1](../user-manual.md#_7-1-sanity-orifice-hand-calc)).

The source tree also exports further hand-checkable cases that are deliberately kept out of the menu: a hydrostatic column, a 50/50 split, equal-temperature mixing, tank equalization, and a conduction ladder with lumped cooldown. The test suites assert on them. The tolerances are published: 10 Pa on the hydrostatic column, 0.001 kg/s on the split, 0.05 K on mixing ([§8.2](../user-manual.md#_8-2-analytic-verification)).

## CI tiers that actually run the science

A validation suite that runs only when someone remembers to run it does not count as evidence. The tiers are defined in [CONTRIBUTING.md](../../CONTRIBUTING.md), [docs/testing-slow.md](../testing-slow.md), and the CI workflow:

| Tier               | What it runs                                                                                             | When CI runs it                                                                  |
| ------------------ | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `npm test`         | Fast tier: component, solver, configuration, UI, server, workflow tests; excludes whole scientific files | Every pull request (`check` job, with lint, format, typecheck, production build) |
| `npm run test:all` | Every Vitest file, including real-fluid, two-phase, chilldown, venturi, and benchmark suites             | Every pull request (`scientific-validation` job)                                 |
| `RUN_SLOW=1`       | Adds opt-in blocks: full NBS chilldown baselines, cavitating-venturi sweeps, two-phase staircases        | Pushes to `main`, weekly schedule (Mondays), manual dispatch                     |
| Playwright e2e     | Full browser suite against the production build                                                          | Every pull request, four shards                                                  |
| Python wheel       | Installed-wheel tests on Linux, macOS, Windows                                                           | Every pull request                                                               |

The fast tier excludes expensive scientific suites by whole file, not by test-name filter, so that "suite membership is reviewable and stable" ([architecture](../architecture.md)). The demo site deploys only after a successful CI run on `main`, so a red `main` cannot reach the published app.

This was not always true. The 0.2.0 changelog entry says the scheduled job "now runs the slow scientific suite (`RUN_SLOW=1`) and the full Playwright e2e suite (previously never run anywhere)." I would rather admit that than pretend the infrastructure arrived fully formed.

## Defects verification caught

This is the section that matters. The [CHANGELOG](../../CHANGELOG.md) records the defects, and a pattern stands out: **most of the serious ones were cases of false success**. Something was reported as converged, valid, or computed when it was not.

- **Microfluidic transients froze, and the solver said they had converged** (0.3.0). The Newton stopping test compared an absolute tolerance against residual rows in kg/s. At microfluidic flows (~1e-8 kg/s), every mass imbalance already passed, so steps were accepted at their warm start. A validation case caught it: a bubble-damped syringe network from Lee et al. (2012), checked against its exact ODE. Before the fix the error was 1.2 % at tol 1e-9 and 37 % at the UI default of 1e-6. Afterwards it was under 1e-3 at both ([microfluidics report](../validation/microfluidics-report.md), case B6).
- **Transient steps were certified as converged unconditionally** (0.2.2). For incompressible, ideal-gas, and compressible-liquid networks, a step was labeled `converged` without checking that the inner Newton had met its residual bar. This hid a real failure: the first step of the **Entrapped-air line** example could not balance its momentum rows, because a warm-start guess was being used as an initial condition behind a closed valve, and the step was reported as converged anyway.
- **A failed chemistry sub-step was silently swallowed** (0.2.2). The node stayed at its pre-reaction state inside a step that was certified as converged.
- **A fabricated property state could reach an accepted result** (0.2.2). A last-resort fallback (`T = 300 K, ρ = 100 kg/m³`), there only to avoid a WebAssembly crash, could pass through unnoticed. Steady solves now report `converged: false` with a fallback count.
- **A fabricated critical point was cached for the life of the process** (0.2.0). A failed CoolProp critical-point read silently cached `Pc = 1e7 Pa, Tc = 300 K`, and that misrouted every later phase-region decision. It now throws.
- **An unknown convection model was evaluated as Darr–Hartwig** (0.2.0), instead of failing loudly.
- **The reported ΔP under `momentumFlux` was not the solved ΔP** (0.2.0). It was re-derived from a legacy formula that disagreed with the default scheme.
- **A sweep could run embedded code that the Run button would have blocked** (0.2.2, security). Sweeps now go through the same trust preflight.

The validation data needed checking too. The NBS chilldown dataset module records that an early comparison had used a model node about 40.6 m down the line against Table 6. Table 6 is defined at station 4, 60.35 m from the inlet, and the mismatch produced a confounded "−27 %…−32 %" error. The same header flags a raw-data catalogue that listed the thermocouple stations wrongly. Both primary sources agree on 20/80/141/198 ft (`src/validation/nbsChilldown.ts`).

The repository does not record which lines a model drafted and which I typed, so I won't pretend to an attribution I can't support. What it does record is the shape of the failures: code that looks complete, returns a number, and says "done." That is the failure mode I now design against. Every defect above is pinned by a regression test, and several of the fixes went the same way: replace a silent fallback with a loud failure.

## Trust levels on experimental data

Experimental validation brings its own ways to overclaim, and the NBS Report 9264 chilldown corpus shows how I handle them. It has 18 Table-6 chilldown-time points and 44 digitized station traces from eleven oscillograph figures. These are not treated as one pool ([§8.4](../user-manual.md#_8-4-validation-against-experiment)):

- **Four saturated runs (sixteen traces) are trusted**, which means calibration-grade.
- **Seven subcooled runs are diagnostic only.** At coarse axial discretization their errors reach +80 %. They may inform a diagnosis, but they may not be quoted as agreement.

The code enforces this too, not just the prose. The corpus validator throws if a subcooled run is not marked `diagnosticOnly`. Per-trace QC flags then further restrict which features of a trusted trace can be used, because the NBS report itself warns that some low-temperature curve crossings are measurement inaccuracies.

## Labeling what is not validated

Every convection correlation has a status in [§8.5](../user-manual.md#_8-5-correlation-status). Dittus–Boelter is standard. Darr–Hartwig is verified structurally against the published equations, with its fitted envelope (LH₂, vertical upflow, 1 g) stated. TT-WF, a design of my own, is labeled **"Research status, not validated."** A custom expression has "no published range; the user owns its validity."

The architecture also enforces a boundary. Production solver code may not import from `src/validation`, and lint rules check this. Validation corpora "must not silently tune runtime defaults to a single experiment" ([architecture](../architecture.md)). A solver tuned to match the very data it is validated against has not been validated by that data.

## What I'd say to anyone doing the same

Here is what I can support from the record. AI assistance made it cheap to produce a large surface area: 19 component types, seven report generators, and the test scaffolding around them. It did not make that surface area correct. The evidence did that, and the evidence caught real defects that would otherwise have shipped looking fine.

If you take one thing from this post, make it the habit I asked for in the README: **check it rather than trust it.** Every report names its reference, tolerance, units, and assumptions. If you find a case where OpenFLUME disagrees with a reference you trust, [open an issue](https://github.com/OpenFLUME/OpenFLUME/issues/new/choose) with the reference and the tolerance. A well-documented disagreement is the most useful contribution this project can get.
